# Product decisions

Answers from the product owner to questions the spec leaves open. These are binding for planning and building.

| Date | Question | Decision |
|---|---|---|
| 2026-10-14 | Password policy | Minimum 8 characters. No complexity rules and no breached-password check. |
| 2026-10-14 | Can users fix bad odometer readings? | Yes. Users can edit and delete individual readings from the odometer history. The vehicle's current odometer and average km/day must be recomputed afterwards. |
| 2026-10-14 | Where to store photos and receipts | Cloudflare R2, accessed through the S3-compatible API (AWSSDK.S3), so the provider stays a config change. Credentials go in user-secrets or environment variables, never in the repo. |
| 2026-10-14 | Hosting | Web app on Cloudflare Pages, files on Cloudflare R2, API on Azure App Service (free tier), database on Azure SQL Database (free offer). Stay on SQL Server and EF Core SqlServer; no switch to Postgres. |
| 2026-10-14 | Default currency | Asked at sign-up. The register form includes a currency picker. |
| 2026-10-14 | Where odometer history lives | On a per-car page (`/cars/:id`) that will later also hold the car's tasks and service history. |
| 2026-10-14 | Odometer reading dates (delegated: owner asked the team to decide; review on return) | Reject readings dated in the future. A reading must fit date order: at least the reading before its date and at most the reading after it, unless the user confirms a correction. The vehicle's current odometer is the latest-dated reading. |
| 2026-10-14 | Initial odometer cap (delegated) | A car's starting odometer uses the same 0 to 10,000,000 km range and `odometer.invalidValue` code as readings. |
| 2026-10-14 | Keyboard focus and Escape (delegated) | Focus after Save goes to the saved row's Edit button. After Delete it goes to the next older row's Edit button, then the newest remaining row, then the section heading. After Cancel or Escape it returns to the opener. Escape closes inline forms. On route change, focus moves to the page's h1. |
| 2026-10-14 | Destructive actions and page titles (delegated) | A red `--danger` token is used only on confirm-Delete buttons. Page titles are `<page> · OnlyCars`. |
| 2026-10-14 | Auth hardening, SEC-1 (delegated) | A deploy gate. Limits: 10 auth requests per 15 minutes per IP; 10 failed logins per 15 minutes per email (accepting a possible 15-minute lockout of a victim); 300 requests per minute per IP globally. Over the limit returns 429 `auth.tooManyAttempts` with `Retry-After`. Counters are in memory, on a single instance. `ForwardedHeaders` is configured for Azure. Login takes constant time through a dummy-hash verify. Model-binding 400s hide .NET type names. |
| 2026-10-14 | Maintenance tasks, MVP2-A (delegated) | Tasks live on `/cars/:id` above the odometer history. Categories are an enum: Oil, Filters, Brakes, Tires, Fluids, Battery, Belts, Ignition, Other. `TaskTemplate` gets a stable `Key` (a deviation from spec Part 2) and its names are translated on the client. Templates are read-only; a user's copy is fully editable. The starter library has 12 generic templates, which the owner should review. Last done is required (no "never done"). Time intervals are entered as days, months (30 days) or years (365 days) and stored as days. Duplicate tasks are allowed. Delete is a hard delete. |
| 2026-10-14 | Due-soon threshold, MVP2-B (delegated) | Percent only, 1 to 50, default 10, using `DueSoonPercent`. No absolute "500 km" option. |
| 2026-10-14 | Ticket order (delegated) | MVP1-C, then MVP2-A, then SEC-1 (backend, built alongside MVP2-A's frontend), then MVP2-B (status), then MVP2-C (Reset and Undo). The settings screen (km/mi, currency, theme, locale) comes after step 2. |
| 2026-10-14 | Stale "last done" on task edits (delegated) | On PUT, the last-done km and date range checks only run when those values change. This keeps the Enabled toggle and other edits working after the car's odometer has been corrected below a task's last-done km. |
| 2026-10-14 | Sign-up reveals existing accounts (delegated) | Accepted: register still returns `auth.emailTaken`. For a personal app this is acceptable while register is rate-limited. Revisit if the app opens to the public at scale. |
| 2026-10-14 | Login lockout identity (delegated, from security review) | The per-email failure counter is keyed on the user's id when the email matches an account (so look-alike Unicode emails share one counter), otherwise on the normalized email. Emails over 256 characters are rejected before any lookup. Account counters are never evicted; if the cache is full when a new one is needed, that login fails closed with 429 (a real user may be briefly locked out during a cache flood rather than leaving the account unprotected). |
| 2026-10-14 | Client IP behind a proxy (delegated, from security review) | Trusting the rightmost `X-Forwarded-For` entry is only right while the API sits directly behind App Service. If it is ever put behind Cloudflare, switch to `CF-Connecting-IP` with the Cloudflare ranges as `KnownIPNetworks`. |
| 2026-10-14 | MVP2-A QA Lows (delegated) | (a) Numeric task names sorting as text ("10k" before "9k"): fixed in MVP2-B, whose urgency sort breaks ties by name with a numeric-aware compare on the client; the server's order stops mattering. (b) The "Add task" picker and an edit form open at the same time: accepted, since no input is lost and each form saves on its own. (c) A failed-toggle error that stays after the next action: fixed in MVP2-B (any new action on a row clears that row's old error). (d) A time interval over 20 years only caught by the server with a combined km/time message: fixed in MVP2-B (the client blocks it and names the field that's wrong). |
| 2026-10-14 | SEC-1 429 in the browser (delegated) | Accepted with the 429 mocked in UI QA. The real limiter is covered by unit tests and the security review's run against a Production build; the dev limits stay high so the smoke suite never trips them. |
| 2026-10-14 | Task status rules, MVP2-B (delegated) | Status is computed on read with the server's UTC date. Km or days used are never below 0 (an odometer corrected below last done, or a last-done date of tomorrow, counts as 0 used). A task is Overdue when either remaining value is below 0, and Due soon when either remaining value is at or below `DueSoonPercent` of its interval (so 0 remaining is Due soon, "due now"). The worse interval decides. Disabled tasks have no status and no remaining values. The list sorts Overdue, Due soon, OK, then Disabled; within a status by most used first. A predicted due date from average km/day is not in MVP2-B. |
| 2026-10-14 | Remaining line in months, MVP2-B (delegated, from code review) | From 60 days up the remaining line shows whole months ("about N months"), and this applies to the overdue text too ("Overdue by 300 km and about 9 months"), so one rule covers both. In Hebrew the two overdue parts are joined with "וגם", because the "ו־" prefix needs a code change to handle both the number and the "כ־N חודשים" forms; the owner may want that changed. |
| 2026-10-15 | MVP2-B QA Lows (delegated) | (1) A failed task reload after an odometer change replaces the rows with the error: fixed in MVP2-C, because Reset and Undo also reload the list. When rows are already showing, a failed reload keeps them and shows the error above them; only a first load with no rows shows the error alone. (2) "about 243" and "months" breaking across lines on English mobile: fixed in MVP2-C with a non-breaking space between the number and the unit word in the remaining and overdue strings, in `en` and `he`. (3) The progress bar's `aria-valuetext` reading "177%" while `aria-valuemax` is 100: accepted. The bar is full at 100, and the text tells a screen-reader user how far past due the task is, which the visible "Overdue by" line also says. |
| 2026-10-15 | Reset / Mark as done, MVP2-C (delegated) | One tap records the car's current odometer and today (the client sends its local date; the server accepts UTC today plus or minus 1 day and defaults to UTC today). Cost and notes are optional and entered in an expansion; there is no odometer or date field, so backdated services wait for step 3's service record form. A reset creates a `ServiceRecord` (`ShopName` null, so DIY; `TotalCost` nullable, null when skipped), one `ServiceRecordTask`, sets the task's `LastDone*`, and logs an `OdometerReading` with `Source = Service` linked to the record. That reading skips the date-order checks, because its value is the current odometer. Reset is only offered on enabled tasks of active cars in the UI; the server does not block other cases, matching the existing archived-car behaviour. Cost: 0 to 1,000,000 in the user's currency, 2 decimals. Notes: up to 1,000 characters. |
| 2026-10-15 | Undo for resets, MVP2-C (delegated) | Undo voids the record (`IsVoided = true`), deletes its linked service reading and recomputes the odometer, and restores each linked task's `LastDone*` from a snapshot taken at reset time (`PreviousLastDoneOdometerKm` and `PreviousLastDoneDate` on `ServiceRecordTask`). Only the most recent non-voided reset of each linked task can be undone (409 otherwise), so the snapshots always match "the previous non-voided record" in spec Part 2 and also keep any manual edit made before the reset. If the linked reading is the car's only reading, it is kept and turned into a manual reading instead of deleted. In the UI, Undo appears on the row right after a reset and stays until the next action in the tasks section or leaving the page; there is no timer, so it meets WCAG 2.2.1. After that, undo comes with the service history in step 3. |
| 2026-10-15 | Deleting a task that has resets (delegated) | Allowed, with the same confirm as today. The `ServiceRecordTask` rows cascade; the `ServiceRecord`s, their cost and their odometer readings stay as history. |
| 2026-10-15 | Quick-add reading date (delegated, from MVP2-C backend) | The car list's quick-add sends the client's local date (`localToday()`), like every other reading form. Without it, a quick-add just after local midnight is dated UTC "yesterday" and can fail with `odometer.higherThanNext` against a reading (or a reset's Service reading) dated with the local date. Fixed on the client in MVP2-C; the server default stays UTC today. |
| 2026-10-15 | Which reset counts as "latest" for Undo (delegated, from MVP2-C code review) | Ranked by creation time only, not by (Date, CreatedAt). Each Undo snapshot holds the task's values from just before that reset, so undo is only correct in creation order; dates can go backwards because the client sends its local date within the server's ±1-day slack. This replaces "later by (Date, CreatedAt)" in the MVP2-C ticket. Step 3's backdated service records will need their own rule. |

| 2026-10-15 | Settings rules, SET-1 (delegated) | Changing the currency only relabels amounts; stored costs are not converted, and the field says so. It is applied before first paint from the cached user, so a reload doesn't flash the wrong theme. A failed save reverts the control and shows a translated error. |
| 2026-10-15 | SET-1 QA Lows (delegated) | (1) An arrow key pressed while a radio group is saving moves focus to an unchecked radio: fixed in SET-2, which adds a fourth radio group to the same page. | 2026-10-15 | Where the "amounts are not converted" hint goes (delegated) | Only under the currency field on the Settings page, as built. That is where the currency changes. The car page's "Cost (USD)" label already names the currency, and repeating the hint on every cost field adds noise. |
| 2026-10-15 | Distance unit rules, SET-2 (delegated) | Everything stays stored in km and the API keeps speaking km. The client converts with 1 mi = 1.609344 km: on display it rounds to whole miles, and on input it rounds to whole km before sending. A whole-mile value then shows back unchanged, because 1 km is under 1 mile. The unit is saved through `PUT /api/me/settings` (`distanceUnit`: Km or Mi), defaults to Km, and is not asked at sign-up. Limits are shown in the user's unit and rounded down (10,000,000 km is "6,213,711 mi"; 1,000,000 km is "621,371 mi"), so a value the form accepts is never above the server's km cap. Average distance per day shows one decimal in the user's unit. Starter templates show converted values (10,000 km is "6,214 mi"); there are no separate mile templates. The due-soon percent and time intervals don't change. |
| 2026-10-15 | SET-2 QA notes (delegated) | (a) Remaining miles can be 1 off from the shown numbers (953 shown where the displayed interval and readings give 954): accepted. The gap is at most 1 mile. (b) The Hebrew odometer labels say "קילומטראז׳" even in miles: accepted. | 2026-10-15 | Backdated service records, MVP3-A (delegated; replaces "latest by creation time" for Undo) | A recorded service's date can be any day up to today (no future dates) and its odometer reading follows the same date-order rules and `confirmCorrection` as manual readings. A linked task's `LastDone*` moves to the record only when the record is at least as recent as the task's current last done (by date, then odometer), so entering an old service never makes a task look less recently done. Undo works on any non-voided record, in any order (`serviceRecord.notLatest` is retired): each linked task whose current `LastDone*` equals the voided record's date and odometer is recomputed from the latest remaining non-voided linked record (by date, then odometer, then creation time); with none left, it gets the `PreviousLastDone*` snapshot of its earliest-created linked record. Tasks whose last done came from somewhere else (a later record or a manual edit) are left alone. |
| 2026-10-15 | Void recompute, corrected (delegated, from MVP3-A code review) | Replaces the "earliest-created snapshot" fallback in the 2026-10-15 backdated-records rule, which could wipe out a manual edit (undo A, edit by hand, reset B, undo B went back past the edit) and could move last done backwards (voiding a reset fell back to an older backdated record). New rule, only for tasks whose last done still equals the voided record: start from the voided record's own `PreviousLastDone*`; while that value equals another voided linked record's (date, km), replace it with that record's `PreviousLastDone*`; then take the later, by (date, km), of that base and the latest remaining non-voided linked record. |

| 2026-10-15 | Line items and editing, MVP3-B (delegated) | History rows get **Edit** and **Delete**. Delete is the existing void (soft delete with the task recompute), so the history's "Undo service" button becomes "Delete"; the Undo bar right after Mark done keeps its name. Edit changes shop, total cost, notes and line items. Date, odometer and linked tasks are not editable in MVP3-B (changing them moves readings and task last-done values); the edit form says to delete and record again, and editing them is MVP3-D. Line items (`ServiceItem`): `Description` required, 1 to 100 characters; `Brand` up to 100; `PartNumber` up to 50; `Quantity` above 0 and up to 10,000, 2 decimals (litres, hours); `UnitCost` 0 to 1,000,000, 2 decimals; `IsLabor` (a labour row's quantity is hours). Up to 50 items per record. When a record has items, `TotalCost` is their sum (quantity times unit cost, rounded to 2 decimals) and is computed by the server; the total field becomes read-only and shows the sum. Without items, `TotalCost` is entered by hand as now. A sum over 1,000,000 returns `serviceRecord.invalidCost`. Saving the items replaces the record's whole list. Voided records can't be edited (409 `serviceRecord.alreadyVoided`). The one-tap reset stays without items. |
